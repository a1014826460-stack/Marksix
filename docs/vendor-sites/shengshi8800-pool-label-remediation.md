# tw8800（shengshi8800）前端预测模块“池标签渲染”整改清单

## 结论摘要

tw8800 前台是 legacy shell `frontend/public/vendor/shengshi8800/index.html`，它通过
`static/js/*.js` 逐个模块请求 `httpApi + /api/kaijiang/<endpoint>`（走
`frontend/app/api/kaijiang/[[...path]]/route.ts` 兼容层，最终读 `/api/legacy/module-rows`）。

多数模块的 `mode_payload_*` 历史行是 `标签|号码列表` 结构（例如
`["3头|30,31,...,39"]`）。**缺陷模式**：渲染器只把 `|` 左侧的“池标签”写进预测槽，
`|` 右侧的号码列表被计算后丢弃，于是“本期预测”退化成只有几种取值的分类标签；
取值少（二值）的模块就会表现成“每期都是同一个结果”（家野中特即属此类）。

本清单逐个核对 `site_page_dependencies.py` 中 `site_key="shengshi8800"` 登记的全部模块，
按“渲染缺陷是否真实存在 + 当前展示值可变化程度”分级。

统计时间（本地库快照）：2026-09-27T12:12:04+00:00  
登记模块总数：**41**  
分级分布：P1 **5**、P2 **8**、P3 **3**、无需整改 **25**

## 全站判定整改：只有命中才显示「准」

用户要求：**判断正确为「准」，不正确则不显示**（本次实现统一显示「错」，未开奖/无法判定不显示）。

审计结果：tw8800 legacy 页面实际加载 **42 个**预测脚本，其中 **30 个**把「准」写死在结果旁
（或在共享 `handleSelect.js:getResult()` 里写死），**没有任何判定逻辑**，因此每期都显示「准」。

统一整改方案：

- 新增 `static/js/legacy-prediction-verdict.js`（无依赖，最先加载），提供唯一判定入口：

  | 结果 | 显示 |
  | --- | --- |
  | `ok`（命中） | 「准」 |
  | `miss`（未命中） | 「错」 |
  | `pending`（未开奖） | 不显示判定 |
  | `unknown`（文本类/无候选，无法核对） | 不显示判定 |

- 判定维度按**数据实际维度**自动选择（避免按模块名猜错）：
  池里出现生肖 → 比特码生肖；池里只出现号码 → 比特码号码；类别标签（大小/单双/波色/半波）→ 比类别。
- 30 个脚本改为调用该入口，不再出现写死的「准」；`003dxzt.js` / `dx.js` / `015maishazs.js` /
  `031dssx.js` 保留各自内联判定（口径与统一入口一致）。
- 明确**不显示判定**的模块：文本类 `1.js`(244 诗句)、`017yuqian.js`(62 无候选)、
  `030ym.js`(59 段子)、`028sj.js`(50 文本未命中口径待定)；`023sqzt.js`(197) 前台本来只显示「中几期」。

验证：

- 静态契约 `frontend/test/shengshi8800-legacy-verdict-contract.mjs`：42 个脚本里除判定输出外不得出现写死的「准」。
- 真实接口数据 340 行独立复算：`ok` 必为真命中、`miss` 必为真未命中，0 处不一致。
- 真实浏览器（Playwright + 本地 dev server + 本地 Python API）逐行核对 153 行：
  显示「准」46 行、显示「错」15 行，**未出现任何“未命中却显示准”**。
  过程中还借浏览器核对发现并修掉两个真实缺陷：
  1. `9xiao.js`(49) 等“生肖池 + 配码”模块被按号码池误判 → 改为生肖优先；
  2. `58 半波` 的号码池判定口径修正。

## 分级口径

| 级别 | 判定 | 含义 |
| --- | --- | --- |
| P1 | 仅池标签且展示值 ≤2 种，或渲染值恒为空/undefined | 用户必然反复看到同一结果，必须整改 |
| P2 | 仅池标签且展示值 4~6 种；或有号码池但未渲染且标签二值 | 连续期经常重复，建议整改 |
| P3 | 仅池标签但标签按期变化 | 只丢号码池，重复感弱 |
| — | 展示与数据一致（含数据本身无号码的纯生肖/文本模块） | 无需整改 |

> 说明：「content 内含号码」指该 mode 的 `content` 里是否带 `标签|号码` 形式的本期号码。
> 标记为“否”的纯生肖模块（如 mode 43/46/49/42/56/38）也需要 4~6 个号码才能落地成号码，
> 但这些号码来自固定的生肖→号码映射而非行内数据，属于**设计如此**，不在池标签缺陷范围内。

规则要点：

- 只有**尚未写入**的行会被调整；判定依据是库内最近两期 + 本次批量已写入的行。
- 换值时沿用该展示值在**本模式真实模板**里的完整号码池（例如 108 换成“小”时写入 `01..24` 全池），不会出现标签与号码池不一致。
- 找不到合法替代取值时保留原值并写入 `_diversity_warning`，不会阻断生成。
- 规则已登记到 `backend/docs/prediction-module-rules.md` 的 `uniqueness` 列，便于审阅。

> 注意：本次修复只约束**新生成**的期号。已存在历史行（例如 mode 63 库内 2026 年 182~191 期的旧数据）保持原样，
> 其中的连续相同展示值不会被追溯改写。

## 追加修复：「结果恒为正确」的判定缺陷（前端）

用户要求「在前端展示全为正确」的模块必须优化。核对后确认该现象由**同一处写法**造成，
共 4 个渲染脚本、5 个 mode：

| 脚本 | mode | 原缺陷 | 修复后判定口径 |
| --- | ---: | --- | --- |
| `003dxzt.js` | 57 大小中特 | 高亮条件是「特码号码落在本池内」（大/小两池合起来覆盖 01..49 → 恒真），模板又写死「准」 | 预测的 **大/小** 是否等于特码实际大小（≥25 为大） |
| `dx.js` | 108 大数小数 | 同上；结果还走共享 `getResult()`，其内部同样硬编码 `+ "准"` | 同上 |
| `015maishazs.js` | 28 单双中特 | 高亮条件是「特码号码落在本池内」（单/双两池覆盖 01..49 → 恒真），模板无判定 | 预测的 **单/双** 是否等于特码实际单双 |
| `031dssx.js` | 31 单双四肖 | 结果后直接写死「准」；高亮条件「特肖落在单组或双组」在多数期恒真 | 特码**生肖**是否落在本期两组任一之内（该模块两组是每期变化的 4+4 拆分，并非固定单肖/双肖，故不能用奇偶判定） |

行为调整：判定为真显示「准」、为假显示「错」、未开奖不显示判定，高亮只在命中时出现。
共享的 `handleSelect.js:getResult()` 未改动（仍有大量模块依赖它）。

> 尚未处理：`015maishazs.js` 的标题仍是厂商原名「买啥开啥」，与「单双中特」语义不一致，需你确认后再改文案。

## 整改实施建议（按改动面排序）

1. **不要动 `frontend/public/vendor/shengshi8800/static/js/**` 以外的契约**：
   这些脚本只消费 `/api/kaijiang/*` 已经是既有兼容层字段（`content`/`res_code`/`res_sx`/`xiao*`/`tou`/`hei`/`bai`/`jiexi`），
   整改只需改渲染表达式，不新增接口字段。

   `xiao.push(c[0])` / `c.push(\`${xiao[i]}\`)` 改为同时输出 `c[1]`，例如
   ```js
   let c = [];
   for (let i in content) {
     let [label, pool] = content[i].split('|');
     c.push(hit ? `<span style="background-color:#FFFF00">${label}|${pool}</span>` : `${label}|${pool}`);
   }
   ```
   命中判定继续用现有 `code/sx in pool` 逻辑，不改变语义。

3. **P2/P3 的号码池渲染（本次未改）**：`009stzt.js`(12)、`024jsyw.js`(20)、`021qqsh.js`(26)、

## 数据快照说明

清单中的“展示值种类 / 最常见展示值”取自**本次本地 `liuhecai` 库快照**
（web_id=4、lottery_type_id=3、最多 10 行）。`created.mode_payload_*` 由本地 worker 持续生成，
因此某个模块的具体重复次数会随后续期号变化；但**“展示值种类上限由渲染器决定”这一结论与数据快照无关**：
例如 mode 63 永远只有 `家禽` / `野兽` 两种可能，mode 57 永远只有 `大` / `小` 两种可能。

### 3. 三期中特（mode 197）「中1期」

原渲染把 `中1期` 写死（未开奖时显示 `中几期`）。曾改为由 compat 路由
`frontend/app/api/kaijiang/[[...path]]/route.ts` 的 `sanqiWindowZodiacs()` 汇总
**同一三期窗口内已开奖各期的特肖**（`period_zodiacs`），前台统计真实 `中N期`。

**2026-09-28 反转**：确认厂商口径就是固定文案——厂商对已开奖窗口一律显示 `中1期`
（`let term = '中1期'; if (!sx) term = '中几期'`），从不显示中0期/中2期/中3期；
真实期数统计会暴露「中0期」，不符合厂商营销展示。现恢复固定口径：
窗口内已有开奖 -> `中1期`；一期都没开奖 -> `中几期`。`period_zodiacs` 保留，
继续用于命中生肖标黄（窗口内已开奖各期的特肖落在候选 4 肖内即高亮）。

### 4. 跨脚本全局名冲突（判定被静默覆盖）

`015maishazs.js`（28）与 `031dssx.js`（31）都定义了 `window.__parityVerdict`，
`003dxzt.js`（57）与 `dx.js`（108）都定义了 `window.__sizeVerdict`。
由于 HTML 里的加载顺序，后加载的实现会覆盖前一个：

- 单双四肖（31）实际按“号码单双”判定 → 188 期特肖蛇明明在单组却显示 `错`；
- 大小系列两份实现恰好相同，所以没有暴露。

现全部移除，统一走 `window.legacyPredictionVerdict`；并新增契约检查，
禁止任何供应商脚本定义跨脚本重复的 `window.__*` 全局。

### 5. 展示唯一性：mode 52 纳入规则、mode 62 改为相邻 5 期

- `THREE_PERIOD_UNIQUE_MODE_IDS` 增加 **52 四字玄机**（展示值 = `title`），
  避免 live 页面出现连续 6 期同一标题（`黯然無光`）。
- 新增 `DISPLAY_UNIQUE_WINDOW_BY_MODE = {62: 5}` 与 `display_unique_window()`：
  62 欲钱解特诗候选池最大（本地 41 条真实诗句），要求**相邻连续 5 期**不得相同；
  其余托管模式仍为 3 期。
- 62 的候选来源补充 `TEXT_POOL_SOURCES["欲钱解特"] = ("mode_payload_62", "title")`，
  `format_juzi_title()` 在 `text_history_mappings` 缺 mode 62 行时回退读取
  `public.mode_payload_62` 的真实诗句，生成端不再落 `欲钱解特诗` 占位串。

### 6. 明确不判定（无候选可核对）

`62 欲钱解特`、`244 一语破天机` 的接口只返回上一期正文（`content` / `title`），
没有本期候选生肖或号码，**无法核对**，因此不显示「准/错」。
若需要展示判定，需在数据侧补充候选字段（属后续改动，本轮未做）。
