# API 契约保护下的后端增量优化 — 设计文档

2026-06-27

## 概述

本次优化目标不是重写后端，而是在 **不改变前端依赖的 API 返回数据结构、字段名、兼容路径和状态语义** 的前提下，先做一轮低风险、可验证的内部收口。

优化重点放在三件事：

1. 为关键前端依赖接口建立契约保护测试，锁定返回结构
2. 修正文档、入口命名和运行告警中的实现偏差
3. 增强启动期安全提示与部署风险可见性

本轮不调整业务查询结果，不重写调度器，不改预测生成算法，不做跨模块大规模拆分。

---

## 一、目标与边界

### 1.1 目标

- 在现有代码基础上提升可维护性和可读性
- 为后续更深层的重构建立“前端 API 不变”的测试护栏
- 消除 README 与真实实现之间的关键偏差，降低接手和排障成本
- 对高风险运行条件提供显式告警，避免默认配置误入生产

### 1.2 强约束

以下内容必须保持不变：

- 前端实际依赖的 API 路径
- 关键 API 的 JSON 顶层结构
- 关键字段名、字段类型和兼容字段
- 成功/失败时的主要状态码语义
- 旧站兼容接口的响应格式

### 1.3 本轮不做

- 不修改前端调用方式
- 不修改数据库 schema 的业务字段语义
- 不修改预测生成结果格式
- 不修改公开或管理接口的返回字段集合
- 不把调度器迁移为独立服务
- 不移除 SQLite 兼容分支，只做文档和边界收口

---

## 二、优化策略

### 2.1 总体策略

采用“先保护、再收口”的顺序：

1. 先补 API 契约测试，确认测试能在改动前失败或覆盖到目标行为
2. 再进行内部低风险优化
3. 每一步优化后运行针对性测试，确认返回未变化

### 2.2 本轮优化范围

#### A. API 契约保护测试

为下列高风险接口补充或增强测试：

- `GET /api/health`
- `POST /api/auth/login`
- 典型 `GET /api/admin/*` 列表接口
- 典型站点上下文相关接口
- 旧站兼容接口，例如 `/api/kaijiang/*`、`/api/post/getList`

测试关注点：

- 状态码
- `Content-Type`
- JSON 顶层结构
- `ok`、`error`、`data`、`items` 等关键字段是否存在
- 旧接口的兼容响应包装是否保持不变

测试实现优先使用现有单元测试体系，必要时补轻量集成测试，但不引入新测试框架。

#### B. 文档与入口收口

修正文档和注释中的以下偏差：

- README 中 `http/` 与实际 `app_http/` 不一致
- README 中提到的 `backend/src/config.yaml` 与当前仓库实际情况不一致
- README 中仍引用部分已迁移的旧文件路径
- 入口文件 `app.py` / `main.py` / `app_http/server.py` 的职责说明需要统一

目标是让新接手的人按文档就能找到真实入口和真实配置源。

#### C. 启动期安全与风险告警

在不影响现有 API 返回的前提下，增强运行时可见性：

- 检测默认管理员密码仍为初始化值时输出明确告警
- 检测当前调度器为单进程内调度时输出部署提示
- 检测正式运行未显式配置 PostgreSQL 目标时保持现有失败语义，但补足说明

这些增强仅影响日志/控制台输出，不影响接口返回内容。

## 三、测试设计

### 3.1 测试原则

- 先覆盖“响应形状”，再优化内部代码
- 不把测试写成实现细节快照，而是写成 API 契约断言
- 对已有测试保持增量补充，不大规模改写测试体系

### 3.2 测试分层

#### 单元测试

适用于：

- `Router` / `RequestContext` 错误响应形状
- 认证失败时的返回结构
- 兼容层函数返回包装结构

#### 轻量集成测试

适用于：

- 关键 HTTP 路径实际返回的 JSON 结构
- 管理接口与旧接口的响应兼容性

如测试依赖数据库，优先复用现有测试夹具和最小必要种子数据。

### 3.3 验收标准

本轮优化完成后，需要满足：

- 新增契约测试全部通过
- 原有相关单元/集成测试通过
- 改动前后关键接口响应形状无差异
- 无新增前端需要适配的接口变更

## 四、实现设计

### 4.1 契约测试文件组织

优先在现有测试目录中增量增加：

- `backend/src/tests/unit/`：纯响应组装、兼容包装、错误结构
- `backend/src/tests/integration/`：关键 API 路径契约

命名倾向：

- `test_api_contract_auth.py`
- `test_api_contract_admin_routes.py`
- `test_api_contract_legacy_routes.py`

具体文件名可结合当前测试风格微调，但目标要一眼可见。

### 4.2 文档修正范围

主要更新 [README_CN.md](/abs/path/D:/pythonProject/outsource/Liuhecai/backend/README_CN.md)：

- 明确 `app.py` 是兼容入口，`main.py` 是 canonical entry，实际服务实现位于 `app_http/server.py`
- 明确运行时配置核心在 `runtime_config.py` + 数据库 `system_config` + `DATABASE_URL`
- 删除或改写不存在的 `backend/src/config.yaml` 说法
- 将 `crawler/crawler_service.py` 说明更新为兼容导出层，真实实现位于 `crawler/scheduler.py`

### 4.3 启动期告警实现

在不改变外部行为的前提下，增加启动日志：

- 默认管理员密码告警
- 单进程调度器告警
- 正式运行仅支持 PostgreSQL 的说明统一化

这些告警应放在启动路径附近，优先考虑：

- `app_http/server.py`
- `runtime_config.py`
- `auth.py`

要求：

- 不新增异常分支改变现有接口返回
- 不修改数据库中的默认值写入逻辑
- 不影响测试环境的正常启动

## 五、风险与控制

### 5.1 主要风险

- 测试补得不准，误把实现细节当契约
- 文档修正与真实代码再次偏离
- 启动告警位置选得不好，导致重复输出或测试噪音

### 5.2 控制措施

- 契约测试只断言前端真正依赖的结构，不断言无关字段排序或内部日志
- 文档修正前逐一对照真实文件和实际入口
- 告警优先使用日志输出，避免改动核心控制流
- 每个小改动后运行对应测试，而不是最后一次性回归
