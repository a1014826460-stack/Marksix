# 预测资料生成硬约束设计

日期：2026-07-18  
状态：待用户复核

## 目标

在不改变任何 HTTP API 路径、字段、字段顺序或 legacy 包装的前提下，为后台预测资料生成建立可验证的四项约束：

1. 对已预设未来开奖结果的台湾彩预测，按站点和模块保证任意连续 10 期至少 6 期命中。
2. 生成器可在内部读取未来开奖真值；生成的候选可恰好包含真值对应的候选项，但不得向 HTTP 响应、结果字段、日志、任务摘要或图片文本输出完整未来开奖号码。
3. 同一期、同模块的不同站点，按玩法规定的前缀宽度 `N` 强制不同。
4. 同站点、同模块的相邻期完整预测签名强制不同；生成中期的前一期或后一期已存在时，两边都必须比较。

## 已确认的业务决定

- 正确率 `60%` 定义为：任意连续 10 个受控期次至少 6 个命中，而不是长期随机期望为 60%。命中数可为 6 到 10。
- 未来期开奖明文仅允许在后台生成事务的内存中读取。
- 预测正文中出现一个由玩法规则选择出的号码、生肖、尾数或分类标签是允许的；这属于预测候选，不单独构成泄露。
- `res_code`、`res_sx`、`res_color`、完整七个开奖号码、`DrawTruth`、控制目标、命中状态和真值派生调试信息不得出现在外部 API、前台 history、图片文字、日志或任务摘要中。
- 无法证明命中规则或无法构造受控命中/不中候选的模块，不得宣称满足准确率保证；未来受控生成须明确跳过并记录内部不含真值的原因，直到补齐规则定义。

## 方案对比

### 方案 A：单期概率加连续次数限制

保留当前确定性随机和最多连中/连错逻辑。

- 优点：改动小。
- 缺点：不能保证任意 10 期至少 6 中，重启和补跑也会丢失状态。
- 结论：不采用。

### 方案 B：内存滚动窗口与种子差异化

在批次内根据前 9 期安排命中，并继续依赖 `web_id` 种子。

- 优点：可改善单次批量生成。
- 缺点：不能覆盖重启、并发、跨批次和跨站碰撞；种子不构成唯一性保证。
- 结论：不采用。

### 方案 C：持久化控制账本与签名预约（采用）

在数据库内保存每个受控生成期的目标命中、规则版本和规范化预测签名，并在一个事务中完成滚动计划、跨站预约、相邻期检查和预测正文写入。

- 优点：可证明 10 期下限，支持补跑/重跑/多进程，并可由数据库约束防止并发碰撞。
- 缺点：需要新的内部表、规则 manifest 和迁移测试。

## 架构

### 规则 manifest

新增内部 `PredictionGenerationRule` 注册表，按静态 `mode_id` 和动态配置构建规则。每条规则固定声明：

- `rule_id` / `rule_revision`
- 玩法类别、候选提取器和规范化签名提取器
- 真实结果转换器（只读 `DrawTruth`，输出本玩法的原子 outcome）
- 命中判定器（与 `PredictionConfig.hit_checker` 一致）
- 能否构造命中和不中候选
- 跨站前缀宽度 `cross_site_prefix_width`
- 同站相邻期签名策略
- 是否允许未来受控生成及其原因

不得再以 `PredictionCategory` 的泛化标签代替具体玩法 outcome。头、尾、五行、波色、结构映射、混合维度和排除玩法均由本玩法规则产生 outcome 后，再调用自己的 `hit_checker`。

`mode_id=470` 的规则为：候选为有序的 3 个生肖；特码生肖出现在任一候选中即命中；跨站前缀宽度为 1；相邻期比较 3 个生肖的完整有序签名。

默认的前缀宽度以 manifest 明确列出，而不是从随机种子推断：

- 单候选、3 候选和一般结构化玩法：1。
- 6 候选玩法：2；9 候选玩法：3；大集合号码玩法：按规则显式设为 2 或 3。
- 多列玩法：每个业务维度的第一个候选组成前缀签名。
- 文本和图片玩法：使用可替换的源记录/候选签名；没有足够候选容量时拒绝写入而非降级。

实现时会为每个现有 mode 写出实际宽度，并由文档生成器列出，供管理员复核。

### 持久化控制账本

新增内部表 `prediction_generation_controls`，仅供 domain/repository 使用。其记录不属于 created 预测正文，也不被任何 API 查询。核心字段包括：

- `lottery_type_id`, `year`, `term`, `mode_id`, `web_id`
- `target_hit`、`verified_hit`、`rule_id`、`rule_revision`
- 完整签名哈希、跨站前缀哈希（只保存规范化候选，不保存完整未来开奖号码）
- 生成时间、生成来源和替换版本

唯一键保证一个站点在同一期同模块只有一个受控记录。对 `(lottery_type_id, year, term, mode_id, prefix_hash)` 建立跨站唯一性约束；生成事务先获得该期模块范围的 PostgreSQL advisory transaction lock，再预约签名，避免两个站点并发获得相同前缀。

旧 created 记录若没有控制账本，不计入“保证窗口”。首次受控生成前会以实际规则和未来真值验证可恢复的旧记录；无法验证的记录标为需要管理员重建，不会伪造它们的命中状态。

### 正确率计划

对同一 `(lottery_type_id, web_id, mode_id)` 以期号升序读取前 9 条已验证控制记录，再为当前期选择目标：

1. 计算包含当前期的 10 期窗口中，达到 `ceil(10 * target_hit_rate)` 所需的最少命中数。
2. 若当前期必须命中才能满足窗口下限，则强制命中；否则按稳定种子在允许的命中/不中中选择。
3. 生成候选后，使用规则 manifest 对真实 outcome 复算 `verified_hit`。只有 `verified_hit == target_hit` 才可写入 created 表和控制账本。
4. 对已有后续期的补跑或覆盖，预先重新校验受影响的所有滚动窗口；若会破坏任一窗口，整个事务拒绝写入。

该机制保证“至少”要求，不将 60% 错误解释为“恰好 6 中”。配置需增加内部 `window_size`（默认 10）和 `minimum_hit_rate`，并与现有 `target_hit_rate` 保持兼容映射；HTTP 请求与响应不新增字段。

### 多样性

生成候选后、写入前在同一事务内执行：

1. 跨站检查同彩种、同一期、同模块其它 `web_id` 的前缀签名；冲突则由规则提供替代候选并重新验证命中目标。
2. 检查同站相邻的 `(year, term)` 两侧已有完整签名；相同则重选。
3. 对文本、图片和复杂多列玩法，签名来自规则定义的业务候选/源记录，而非只解析 `content` JSON。
4. 候选空间耗尽、规则不支持替换或数据库唯一键冲突时，回滚本期生成并报告非敏感业务错误；绝不带 `_diversity_warning` 继续写入。

一个玩法若可用前缀数小于同一期需生成站点数，视为配置容量不足，阻止生成并在规则文档中标明容量，而不是降低约束。

### 未来真值安全

`DrawTruth` 保持内部对象。受控生成完成后仅保留预测正文和不含真值的控制摘要。安全测试使用唯一的完整开奖 CSV 哨兵，验证：

- `/api/predict/{mechanism}`、管理端预测接口、公开 history 和 legacy 接口均不包含完整哨兵或结果字段。
- created 预测行的未来 `res_code`、`res_sx`、`res_color` 为空。
- 任务日志、模块报告、异常和图片渲染输入不包含完整哨兵。
- 候选正文允许出现符合规则的单一号码/生肖；测试只禁止完整开奖号码和内部控制字段。

## 模块规则文档

新增 `backend/docs/prediction-module-rules.md`，由 manifest 生成并在测试中校验。每行至少列出：

- `mode_id`、机制 key、标题、规则类别
- 真值 outcome、命中/排除语义、候选数量
- 正确率控制支持状态、跨站前缀宽度、相邻期签名形式
- 未来真值使用范围和禁止外泄字段

动态模块若无法从 title/列结构得到可验证规则，文档显示为 `blocked_pending_rule`，不能进入“保证准确率”的未来受控队列。

## API 兼容性

- 不修改请求或响应 JSON 字段、字段顺序、HTTP 状态和 legacy 包装。
- `/api/predict/{mechanism}` 仍不读取 future truth。
- 批量生成现有报告的结构不扩展真值、签名或控制计划；新增内部日志也只记录计数、mode、site、期号和非敏感原因。
- 现有预测 content 形状由各 formatter 保持；仅当为满足已确认的准确率或多样性规则而选择不同的合法候选时，正文值会变化。

## 验证

1. 对 60% 配置生成跨批次、跨进程的 20 期数据，逐个滑动 10 期窗口验证至少 6 中。
2. 覆盖命中、不中、包含与排除、生肖、号码、头、尾、波色、五行、混合、多列、图片和文本规则；未验证玩法必须被阻止。
3. 为 mode 470 验证不同 `web_id` 同一期的第一生肖不同，且同站相邻期三个生肖完整签名不同。
4. 覆盖并发两个站点生成同一期，验证数据库只允许一个前缀预约，另一个自动重选或安全失败。
5. 以完整未来开奖哨兵运行生成和 HTTP/legacy/public 路径，断言无完整真值和结果字段泄露。
6. 运行既有 API 契约测试以及完整 `python -m pytest -q`，确认 API 数据结构未变化。

## 分阶段实施

1. 建立规则 manifest、纯命中校验器、规则文档生成器和测试矩阵；先标记无法证明的模块。
2. 引入控制账本、数据库迁移、滚动窗口计划和事务锁；先接入 mode 470、号码、生肖、头尾、大小单双和排除玩法。
3. 接入复杂结构、mixed、文本和图片模块；为每项增加专属签名和可控候选适配器。
4. 删除旧的 best-effort diversity warning 路径，补齐泄露、并发、补跑和全量回归验证。
