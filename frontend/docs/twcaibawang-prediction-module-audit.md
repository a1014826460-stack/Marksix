# twcaibawang 首页预测资料逐块盘点

本清单只针对 `frontend/public/vendor/twcaibawang.com/index.html` 首页当前可见资料块，目标是明确：

1. 哪些块可以直接接现有后台预测机制
2. 哪些块只能部分复用，需要新增聚合层或新的 payload
3. 哪些块本质是文章页、榜单页、静态图库，不属于标准预测模块

## 总结

`twcaibawang(web_id=5)` 首页不是单一的“预测模块列表”，而是 4 类内容混排：

1. 标准预测历史块
2. 组合型预测块
3. 榜单 / 文章跳转块
4. 静态图片 / 图库 / 免责声明块

当前最稳妥的接入策略仍然是：

1. 先接“标准预测历史块”
2. 再补“榜单 / 文章详情接口”
3. 最后处理“组合型预测块”和“展示结构不完全同构”的块

## B. 可复用现有后台能力，但需要二次确认或轻度适配的块

这类块和现有机制“高度相似”，但还不建议在未核样本数据前直接判定为已完成。

| 首页块 | 页面标识/位置 | 候选后端能力 | 当前判断 | 原因 |

| 家野各三肖 | 注释 `<!--家野各三肖-->` | 站点已存在 `mode_id=63` 相关数据 | 需核 payload | 页面是“家三肖 + 野三肖”双列结构，不是普通单列 6 肖 |

### 这类块的建议

1. 先从 PostgreSQL 的 `mode_payload_tables` 和 `created/public.mode_payload_*` 中找真实来源
2. 确认字段是否和首页展示结构一致
3. 如果只是字段名差异，做前端映射或轻量 compatibility adapter
4. 如果结构不一致，再升级为“组合型新接口”

## E. 建议优先级

### 第一优先级：直接接现有后台

优先把下面这些块纳入 `site_prediction_modules` 的精确映射：

- 平特一肖
- 平特一尾
- 大小中特
- 双波
- 琴棋书画
- 四字平特
- 一句爆特
- 赚钱九肖
- 24码
- 三期特码计划
- 三头中特
- 九肖12码
- 必杀一肖
- 绝杀一波

### 第二优先级：文章接口

补下面两类接口即可覆盖首页榜单跳转：

1. `GET /api/vendor/articles?site_id={site_id}&category={category}&term={term}`
2. `GET /api/vendor/articles/{slug}`

建议最小字段：

- 列表：`id`, `slug`, `title`, `term`, `category`, `href`, `updated_at`
- 详情：`id`, `slug`, `title`, `html`, `text`, `source_file`

### 第三优先级：组合型块

优先处理这几个首页最显眼、但当前最不标准的块：

1. `五肖五码`
2. `公开一肖一码`
3. `双波12码`
4. `输尽光`
5. `大小+2头`

## F. 现阶段不需要新加的后台公共接口

当前阶段不需要为了 `twcaibawang` 单独新增这些公共能力：

- 专属开奖 API
- 专属历史开奖 API
- 专属 `pub.js / gg.js` 后端服务
- 专属 draw compatibility 路由

现有可直接复用：

- `/api/public/latest-draw`
- `/api/public/next-draw-deadline`
- `/api/public/draw-history`
- `/api/public/site-page`
- `/api/predict/[mechanism]`

## G. 结论

`twcaibawang` 首页里，已经有一批块可以直接挂到现有后台，不需要新发明整套接口；但首页同样包含不少“组合型块”和“文章型块”，它们不能粗暴地当作标准预测模块处理。

如果按当前仓库的稳妥路线推进，建议把首页块分成三批：

1. 先上线标准预测块映射
2. 再补榜单 / 详情接口
3. 最后逐块处理组合型块

这样不会影响其他站点，也不会误把结构不清楚的块提前标成“已完成动态化”。
